- FLAG (efficiency, not previously noted): the full privileged-group discovery block (`Get-ADGroup -Filter '*' -Properties SID`, then filter by RID suffix/well-known SID) is recomputed from scratch by 7 separate functions -- Find-DormantAccount (644), Get-PrivilegedGroupMembership (778), Find-AdminCountOrphan (890), Find-KerberoastableAccount (960), Find-ASREPRoastableAccount (1025), Find-WeakAccountFlag (1468), Test-ProtectedUsersGap (1524). Each one does a full domain-wide group enumeration independently rather than computing the privileged-group DN set once and passing it in. Notable because domain-specs.md section 2 explicitly documents a *different* optimization ("this optimization matters at scale," re: LastLogon cross-DC queries) as institutional knowledge worth preserving -- the module already cares about this class of problem, just didn't apply the same instinct here. At real domain scale (thousands of groups), this is likely the more expensive repeated query of the two, and unlike the LastLogon case it's not documented anywhere as a deliberate tradeoff.
  - Destination: **Issue** for the fix itself (compute once, pass to callers or cache per-orchestrator-run). Arguably also a one-line **CONTEXT.md** candidate once fixed -- "privileged-group DN set is computed once per Discovery run and threaded through, not per-function" would be a non-obvious architectural fact worth stating so nobody reintroduces the per-function re-query later. Not ADR-eligible on its own -- it's an optimization, not a decision with real alternatives/tradeoffs to justify.
